# Core Banking — Project Context

> این سند مرجع عملی معماری، تصمیم‌های کسب‌وکار، اسکیمای پایگاه داده، وضعیت توسعه و روش همکاری در پروژهٔ Core Banking است.
>
> **اصل بنیادین:** کد باید با اسکیمای نهایی و تصمیم‌های کسب‌وکار هماهنگ شود؛ اسکیمای نهایی برای سازگار کردن کد قدیمی، بدون دلیل روشن و تأیید مالک پروژه، تغییر نمی‌کند.

- **نام مخزن:** Core-Banking

- **چارچوب:** Qt 5

- **نیازمند تطبیق:** اطلاعاتی که ممکن است بین کد محلی، GitHub، اسکیما یا سابقهٔ چت اختلاف داشته باشد.

## 3. هدف و دامنهٔ پروژه

Core Banking یک backend بانکی مبتنی بر API است که به‌صورت تدریجی توسعه می‌یابد. دامنهٔ هدف شامل موارد زیر است:

- ثبت و نگهداری مشتریان؛
- تعریف ارز، جغرافیا و شعب؛
- تعریف انواع حساب و محصولات بانکی؛
- مدیریت سرفصل‌های دفتر کل؛
- نگاشت محصولات به سرفصل‌های حسابداری؛
- افتتاح و نگهداری حساب‌ها؛
- مدیریت مالکیت و اختیارات مرتبط با حساب؛
- ثبت تراکنش‌ها و ورودی‌های تراکنش؛
- ثبت Journal و Journal Entry؛
- ثبت کارمزدها؛
- نگهداری ماندهٔ عملیاتی حساب و ماندهٔ سرفصل؛
- کنترل سازگاری مالی و فراهم کردن امکان تطبیق و حسابرسی.

پروژه هنوز در حال توسعه است. وجود جدول یا کلاس، به‌تنهایی به معنی تکمیل قابلیت، پوشش تمام قواعد کسب‌وکار یا آمادگی برای محیط عملیاتی بانکی نیست.

## 4. اصول معماری

### 4.1 تفکیک لایه‌ها

ساختار اصلی کد از این لایه‌ها تشکیل می‌شود:

- `src/domain/`: موجودیت‌ها و مفاهیم دامنه؛
- `src/application/`: سرویس‌ها و عملیات کسب‌وکار؛
- `src/infrastructure/`: اتصال پایگاه داده و پیاده‌سازی Repositoryها؛
- `src/web/`: HTTP server، router، controller و پاسخ‌های API؛
- `database/schema/`: اسکیمای PostgreSQL و تغییرات آن.

مسئولیت‌ها باید از هم جدا بمانند. کنترلر نباید جای سرویس کسب‌وکار را بگیرد و سرویس نباید وابسته به جزئیات قالب HTTP باشد. Repository مسئول دسترسی به داده است.

### 4.2 اصل API به‌عنوان مسیر واقعی کسب‌وکار

عملیات کسب‌وکار باید از مسیر واقعی برنامه و HTTP API انجام و آزمایش شوند. درج مستقیم داده در پایگاه داده نباید جایگزین آزمایش مسیر واقعی ایجاد مشتری، افتتاح حساب یا ثبت تراکنش شود.

SQL برای تعریف و اعمال migration، بررسی ساختار، عیب‌یابی و کنترل‌های مدیریتی پایگاه داده قابل استفاده است؛ اما این موضوع مجوزی برای جایگزین کردن مسیر کسب‌وکار با درج دستی داده‌های آزمایشی نیست.

### 4.3 تطبیق کد با اسکیما

اسکیماهای نهایی مبنای کار کد هستند. پیش از پیاده‌سازی هر قابلیت:

1. جداول و روابط مرتبط بررسی شوند.
2. محدودیت‌ها، کلیدهای خارجی و مقادیر مجاز بررسی شوند.
3. رفتار کسب‌وکار در سرویس پیاده‌سازی شود.
4. API به سرویس متصل شود.
5. ساخت پروژه و آزمایش HTTP انجام شود.

تغییر اسکیمای نهایی صرفاً به علت ناسازگاری کد قدیمی مجاز نیست؛ هر تغییر ساختاری جدید باید علت مشخص، migration مستقل و تأیید لازم داشته باشد.

## 5. مرزبندی Core Banking و Customer Management

### 5.1 Customer Management

Customer Management سامانهٔ مسئول مدیریت جامع اطلاعات مشتری است. جزئیات کامل مسئولیت‌ها و قرارداد بین دو سامانه در سابقهٔ موجود به‌صورت یک سند مستقل API ثبت نشده است؛ موارد زیر اصول طراحی مورد توافق هستند:

- اطلاعات کامل مشتری در سامانهٔ مدیریت مشتری نگهداری می‌شود.
- Core Banking باید حداقل اطلاعات لازم برای شناسایی و انجام عملیات بانکی را در اختیار داشته باشد.
- عملیات عادی حساب و تراکنش نباید به جست‌وجوی لحظه‌ای در Customer Management وابسته باشد.
- مالکیت اطلاعات و همگام‌سازی تغییرات بین دو سامانه باید در قرارداد مشخصی تعریف شوند.

### 5.2 اطلاعات مشتری در Core Banking

Core Banking اطلاعات پایه‌ای لازم برای انجام عملیات را در مدل مشتری نگهداری می‌کند؛ از جمله:

- شناسهٔ داخلی مشتری؛
- شمارهٔ مشتری؛
- نوع مشتری؛
- کد تابعیت/ملیت؛
- وضعیت مشتری؛
- اطلاعات ضروری شخص حقیقی یا حقوقی که در اسکیمای فعلی تعریف شده است.

این تصمیم به معنی انتقال کل پروندهٔ Customer Management به Core Banking نیست.

**موضوع نیازمند تکمیل:** روش همگام‌سازی، مالکیت هر فیلد، کنترل تغییرات هویتی و رفتار در صورت عدم دسترسی به سامانهٔ مدیریت مشتری باید در قرارداد بین‌سامانه‌ای ثبت شود.

## 6. مدل مشتری

### 6.1 جدول `customer`

اسکیماهای `003_customer.sql` و `004_customer_number_and_indexes.sql` مدل مشتری را تعریف و شمارهٔ مشتری را به قالب ثابت ده‌رقمی تبدیل می‌کنند.

ویژگی‌های اصلی:

- `id`: شناسهٔ داخلی از نوع `BIGINT` و identity؛
- `customer_number`: شمارهٔ مشتری ثابت ده‌رقمی و یکتا؛
- `customer_type`: یکی از `INDIVIDUAL` یا `LEGAL_ENTITY`؛
- `nationality_code`: کد سه‌رقمی که به `country(code)` ارجاع می‌دهد؛
- `status`: یکی از `ACTIVE`، `INACTIVE`، `BLOCKED` یا `CLOSED`؛
- `created_at` و `updated_at`.

شمارهٔ مشتری یک شناسهٔ کسب‌وکاری ده‌رقمی است و نباید با شناسهٔ داخلی پایگاه داده یا شمارهٔ ملی اشتباه گرفته شود.

### 6.2 اشخاص حقیقی

جدول `individual` با `customer_id` به مشتری مرتبط است و فیلدهای زیر را دارد:

- `national_id`؛
- `first_name`؛
- `last_name`.

شمارهٔ هویتی شخص حقیقی یکتا است. ارتباط با مشتری از طریق کلید اصلی مشترک برقرار می‌شود.

### 6.3 اشخاص حقوقی

جدول `legal_entity` با `customer_id` به مشتری مرتبط است و فیلدهای زیر را دارد:

- `legal_id`؛
- `legal_name`؛
- `registration_number` اختیاری.

شناسهٔ حقوقی یکتا است.

### 6.4 وضعیت مشتری

مقادیر مجاز در اسکیما:

- `ACTIVE`
- `INACTIVE`
- `BLOCKED`
- `CLOSED`

تأثیر دقیق هر وضعیت بر افتتاح حساب، برداشت، انتقال و سایر عملیات باید در سرویس‌های مربوطه صریحاً اعمال و آزمایش شود؛ محدودیت پایگاه داده به‌تنهایی این رفتار را تضمین نمی‌کند.

### 6.5 شماره‌گذاری مشتری

شمارهٔ مشتری ده‌رقمی و یکتا است. تاریخچهٔ توسعه به وجود تولیدکنندهٔ شمارهٔ مشتری و آزمایش برخورد شماره اشاره دارد؛ الگوریتم کامل تولید شماره و سیاست retry باید با کد جاری تطبیق داده شود.

## 7. جغرافیا، شعب و ارز

### 7.1 کشور

جدول `country` شامل شناسه، کد سه‌رقمی، نام و محدودیت یکتایی کد و نام است.

کد کشور در این اسکیما به شکل سه رقم تعریف شده است؛ بنابراین نباید بدون بررسی قرارداد دامنه، آن را با کدهای متنی ISO یا کد ارز یکی دانست.

### 7.2 استان و شهر

- `province.country_id` به `country(id)` ارجاع می‌دهد.
- `city.province_id` به `province(id)` ارجاع می‌دهد.
- `011_city_code_global_unique.sql` یکتایی کد شهر را از محدودهٔ هر استان به کل جدول شهرها گسترش می‌دهد.

Migration شمارهٔ 011 ابتدا وجود کدهای تکراری را بررسی می‌کند و در صورت وجود تکرار، به‌جای حدس زدن یا ادغام خودکار داده‌ها، متوقف می‌شود.

### 7.3 شعبه

جدول `branch` دارای `branch_code` هفت‌رقمی، نام، شناسهٔ شهر، وضعیت و زمان‌های ایجاد و به‌روزرسانی است.

وضعیت‌های مجاز شعبه:

- `ACTIVE`
- `INACTIVE`
- `CLOSED`

تصمیم کسب‌وکار ثبت‌شده این است که کد شعبه هفت رقم داشته باشد: سه رقم مربوط به بانک و چهار رقم مربوط به شعبه. قالب دقیق باید در تولید و اعتبارسنجی کد نیز رعایت شود.

### 7.4 ارز

جدول `currency` دارای کد سه‌حرفی، کد عددی سه‌رقمی، نام، `minor_unit`، وضعیت و زمان‌های ثبت است.

`minor_unit` در بازهٔ صفر تا شش محدود شده است. کد ارز و کد عددی آن یکتا هستند.

وجود ارز در جدول به معنی فعال بودن آن برای افتتاح حساب یا انجام تراکنش نیست؛ وضعیت ارز و قواعد کسب‌وکار باید در سرویس‌ها بررسی شوند.

## 8. مدل حساب، نوع حساب و محصول

### 8.1 نوع حساب (`account_type`)

نوع حساب با شناسه، کد دو رقمی، نام، `currency_id`، وضعیت و زمان‌های ثبت تعریف می‌شود.

- کد باید دقیقاً دو رقم باشد.
- کد یکتا است.
- ارز اجباری است.
- وضعیت فقط `ACTIVE` یا `INACTIVE` است.

کدهای کسب‌وکاری مورد بحث در طراحی:

- `01`: جاری؛
- `02`: کوتاه‌مدت؛
- `03`: پس‌انداز؛
- `04`: بلندمدت؛
- `21`: دولتی؛
- `31`: شهرداری؛
- `41`: مدارس و سازمان‌های دولتی.

این فهرست، طبقه‌بندی توافق‌شده در سابقهٔ طراحی است؛ قبل از ثبت این کدها به‌عنوان دادهٔ اولیهٔ رسمی، نام‌ها و کاربرد دقیق هر کد باید با تعریف نهایی محصول و ارز تطبیق داده شود.

### 8.2 محصول (`product`)

محصول دارای کد یکتا، نام، `account_type_id`، `currency_id`، وضعیت و بازهٔ اعتبار است.

- هر محصول به یک نوع حساب متصل است.
- ارز محصول باید با ارز نوع حساب یکسان باشد.
- محصول بازهٔ اعتبار `effective_from` و `effective_to` دارد.
- `effective_to` می‌تواند خالی باشد.
- در صورت وجود تاریخ پایان، نباید قبل از تاریخ شروع باشد.
- وضعیت محصول `ACTIVE` یا `INACTIVE` است.

محصول مفهومی مستقل از نوع مشتری است. نباید برای حقیقی و حقوقی صرفاً به‌دلیل نوع مشتری، محصول تکراری ایجاد کرد؛ مگر اینکه تفاوت واقعی محصول، قواعد یا قرارداد آن را توجیه کند.

### 8.3 وابستگی ارز

طبق تصمیم طراحی ثبت‌شده، نوع حساب نیز ارز مشخص دارد و محصول باید همان ارز را داشته باشد. برای نمونه، حساب جاری ریالی و حساب جاری دلاری دو تعریف مستقل در مدل نوع حساب/محصول هستند؛ جدول مستقل `product_currency` در طراحی فعلی وجود ندارد.

در درخواست افتتاح حساب، کلاینت نباید ارز را جداگانه انتخاب کند اگر ارز از محصول قابل تعیین است. سرور باید روابط محصول، نوع حساب و ارز را اعتبارسنجی کند.

### 8.4 ویژگی‌های آتی محصول

نرخ سود، کارمزد، حداقل مانده، محدودیت‌ها و سایر شرایط قراردادی از ویژگی‌های محتمل آیندهٔ محصول هستند. همهٔ این ویژگی‌ها در اسکیما و کد فعلی الزاماً پیاده‌سازی نشده‌اند.

شرایط زمان‌مند محصول باید طوری طراحی شوند که تغییر تنظیمات جدید، قراردادهای قبلی را بدون تصمیم صریح تغییر ندهد.

- `REVENUE`
- `EXPENSE`

سرفصل می‌تواند والد داشته باشد، اما نمی‌تواند والد خودش باشد. Migration شمارهٔ 010 سازگاری ارز سرفصل با سرفصل والد را نیز با کلید خارجی مرکب اعمال می‌کند.

### 9.2 ارتباط حساب بانکی با سرفصل

هر حساب بانکی در مدل فعلی یک `ledger_account_id` دارد. سرفصل نباید به‌صورت ثابت یا با شناسهٔ هاردکدشده در کد انتخاب شود.

نگاشت محصول به سرفصل باید از دادهٔ پایگاه داده و قواعد اعتبار زمانی استخراج شود.

نمونه‌های مطرح‌شده در طراحی برای کدهای هشت‌رقمی، صرفاً مثال کسب‌وکار هستند و نباید بدون دادهٔ مرجع رسمی به‌عنوان سرفصل‌های موجود فرض شوند.

## 10. روابط حساب و اختیارات اشخاص

Migration شمارهٔ 006 جداول مربوط به مالکیت و اختیارات را تعریف می‌کند.

### 10.1 مالکیت حساب

جدول `account_owner` ارتباط حساب و مشتری را با بازهٔ اعتبار و وضعیت ثبت می‌کند. این مدل امکان چند مالک برای یک حساب را فراهم می‌کند.

افتتاح حساب نباید به مدل سادهٔ «یک مشتری در ستون account» محدود شود، زیرا طراحی نهایی روابط مالکیت جداگانه را پیش‌بینی کرده است.

### 10.2 اختیار حساب

جدول `account_authorization` انواع زیر را در اسکیما تعریف می‌کند:

- `POWER_OF_ATTORNEY`
- `LEGAL_GUARDIAN`
- `LEGAL_REPRESENTATIVE`
- `AUTHORIZED_SIGNATORY`

این جداول برای ثبت رابطهٔ اختیار و بازهٔ اعتبار هستند. مجاز بودن عملیات واقعی باید در سرویس مربوطه بر اساس وضعیت و اعتبار اختیار بررسی شود.

### 10.3 اعضای هیئت‌مدیره و سهام‌داران

- `legal_entity_board_member`: ارتباط مشتری حقوقی با مشتری عضو هیئت‌مدیره، سمت و بازهٔ زمانی؛
- `legal_entity_shareholder`: ارتباط شخص/مشتری سهام‌دار با شخص حقوقی، درصد مالکیت یا تعداد سهام و بازهٔ زمانی.

قواعد کامل درصد مالکیت، جمع سهام، صلاحیت اشخاص و الزامات حقوقی فراتر از صرف کلیدهای خارجی هستند و باید در قواعد کسب‌وکار تکمیل شوند.

### 10.4 دستور یا ساختار امضا

- `account_mandate`: ساختار اختیار/دستور حساب؛
- `account_mandate_party`: طرف‌های مشارکت‌کننده در دستور، از جمله امضاکننده؛
- `account_mandate_rule`: نوع عملیات و تعداد امضاهای موردنیاز.

نوع عملیات‌های تعریف‌شده در `account_mandate_rule` عبارت‌اند از:

- `WITHDRAWAL`
- `TRANSFER`
- `PAYMENT`
- `CLOSE_ACCOUNT`

وجود این ساختار در اسکیما به معنی کامل بودن موتور ارزیابی امضاها در برنامه نیست. اعتبار زمانی، تعداد امضاهای موردنیاز، اشخاص مجاز و نوع عملیات باید پیش از اجرای عملیات حساس ارزیابی شوند.

### 11.1 جدول `account`

جدول حساب شامل شناسهٔ داخلی، شمارهٔ حساب، نوع حساب، محصول، ارز، شعبهٔ افتتاح‌کننده، سرفصل دفتر کل، وضعیت و تاریخ‌های مرتبط است.

الگوریتم نهایی تولید شماره و رقم کنترل باید از کد جاری استخراج و با تست‌های آن تأیید شود؛ از این سند نباید فرمولی حدس زد.

### 11.3 افتتاح حساب

## 12. نگاشت محصول به سرفصل

Migration شمارهٔ 012 جدول `product_ledger_mapping` را اضافه می‌کند.

هدف این جدول:

- تعیین سرفصل دفتر کل برای محصول، نوع حساب و ارز؛
- نگهداری بازهٔ اعتبار نگاشت؛
- حفظ تاریخچهٔ نگاشت‌ها؛
- اتصال حساب افتتاح‌شده به نگاشت مشخصی که هنگام افتتاح استفاده شده است.

ویژگی‌های مهم:

- رابطه با محصول، نوع حساب و ارز با کلید خارجی مرکب کنترل می‌شود.
- سرفصل باید با ارز نگاشت یکسان باشد.
- بازهٔ اعتبار به‌صورت شروع شامل و پایان غیرشامل مدل شده است.
- بازه‌های هم‌پوشان برای یک محصول، حتی اگر نگاشت قدیمی غیرفعال باشد، مجاز نیستند.
- حساب از طریق `product_ledger_mapping_id` به نگاشت دقیق خود متصل است.

بنابراین هنگام افتتاح حساب، انتخاب سرفصل صرفاً بر اساس محصول کافی نیست؛ نگاشت معتبر در تاریخ افتتاح باید پیدا و ثبت شود.

## 13. ماندهٔ حساب و ماندهٔ سرفصل

### 13.1 ماندهٔ عملیاتی حساب

جدول `account_balance` شامل:

- `account_id`
- `ledger_balance`
- `available_balance`
- `updated_at`

هر دو مقدار مانده در اسکیما از نوع `NUMERIC` هستند و محدودیت نامنفی دارند.

ماندهٔ عملیاتی برای خواندن سریع وضعیت حساب استفاده می‌شود. `ledger_balance` و `available_balance` دو مفهوم مجزا هستند و نباید بدون قواعد کسب‌وکار معادل فرض شوند.

### 13.2 ماندهٔ سرفصل

جدول `ledger_account_balance` شامل:

- `ledger_account_id`
- `debit_total`
- `credit_total`
- `balance`
- `updated_at`

این جدول برای خلاصهٔ مانده و گردش بدهکار/بستانکار سرفصل است.

### 13.3 نوع داده و گردکردن

اسکیما در جدول‌های مانده و ثبت مالی از `NUMERIC` بدون precision/scale صریح استفاده می‌کند. از روی این تعریف به‌تنهایی نمی‌توان دقت اعشاری، قواعد گردکردن یا مقیاس نهایی پول را تعیین کرد.

**تصمیم نیازمند تأیید/تطبیق:** نوع دادهٔ مالی نهایی در سطح دامنه و سیاست گردکردن باید از تصمیم‌های قبلی و کد واقعی بازیابی شود. تا آن زمان، این سند precision/scale یا الگوریتم گردکردن جدیدی تعیین نمی‌کند.

### 13.4 ماندهٔ اولیهٔ حساب

افتتاح حساب با ماندهٔ صفر مجاز است. ایجاد حساب صفرمانده به‌خودی‌خود نباید باعث ساخت ثبت حسابداری جعلی شود. در افتتاح صفرمانده، حساب و رکورد مانده ایجاد می‌شوند؛ Journal مالی فقط زمانی ساخته می‌شود که رویداد مالی واقعی نیازمند ثبت داشته باشیم.

- زمان شروع و پایان؛
- شرح و شمارهٔ مرجع.

نوع‌های مجاز:

- `DEPOSIT`
- `WITHDRAWAL`

- `PAYMENT`
- `FEE`
- `REVERSAL`

وضعیت‌های مجاز:

- `INITIATED`

کانال‌های تعریف‌شده:

هر ورودی به یک تراکنش و یک حساب متصل است. نوع ورودی یکی از `SOURCE` یا `DESTINATION` است. مبلغ مثبت، شمارهٔ ترتیب مثبت و ترکیب شمارهٔ ترتیب در یک تراکنش یکتا است.

Migration شمارهٔ 010 تضمین می‌کند ارز ورودی تراکنش با ارز خود تراکنش و ارز حساب مربوطه یکسان باشد.

### 14.3 قرارداد API

در درخواست‌های تراکنش، نوع عملیات باید به‌صورت صریح در JSON تعیین شود و سرور باید مقدار را با فهرست مجاز اعتبارسنجی کند.

این اصل به معنی اعتماد به نوع تراکنش ارسالی کلاینت نیست؛ سرور باید اعتبار مبلغ، وضعیت حساب، ارز، موجودی، اختیارات و سایر قواعد مرتبط را مستقلاً بررسی کند.

## 15. Journal، Journal Entry و کارمزد

### 15.1 Journal

جدول `journal` به تراکنش مرتبط است و تاریخ ثبت، تاریخ ارزش، وضعیت و شرح را نگهداری می‌کند.

وضعیت‌های مجاز:

- `DRAFT`
- `POSTED`
- `REVERSED`

Migration شمارهٔ 010 محدودیت پایگاه داده‌ای قبلی بر رابطهٔ `value_date` و `posting_date` را حذف می‌کند. قواعد تاریخ ارزش، ثبت عقب‌تاریخ و محدودیت‌های مربوط باید در سرویس کسب‌وکار اعمال شوند.

### 15.2 Journal Entry

هر `journal_entry` به Journal و سرفصل دفتر کل مرتبط است و می‌تواند به حساب بانکی نیز ارجاع دهد. ارز، شمارهٔ ترتیب، بدهکار، بستانکار و شرح را نگهداری می‌کند.

محدودیت‌های اصلی:

- شمارهٔ ترتیب در هر Journal یکتا و مثبت است.
- بدهکار و بستانکار منفی نیستند.
- دقیقاً یکی از دو مبلغ بدهکار یا بستانکار باید مثبت باشد.
- در صورت وجود حساب بانکی، ارز و سرفصل ورودی باید با ارز و سرفصل همان حساب سازگار باشند.

اسکیما به‌تنهایی تضمین نمی‌کند که مجموع بدهکار و بستانکار یک Journal برابر باشد. این کنترل باید در منطق ثبت مالی و تست‌های یکپارچگی پیاده‌سازی شود.

### 15.3 کارمزد

جدول `transaction_fee` کارمزد، ارز، نوع کارمزد و سرفصل مربوط را به تراکنش متصل می‌کند.

مبلغ کارمزد باید مثبت باشد. Migration شمارهٔ 010 سازگاری ارز کارمزد با ارز تراکنش و سرفصل کارمزد را کنترل می‌کند.

تصمیم طراحی قبلی این است که کارمزد از سرفصل مستقل خود استفاده کند و شناسهٔ حساب یا جزئیات لازم در شرح ثبت شود؛ شکل نهایی کدگذاری سرفصل‌های کارمزد باید از دادهٔ مرجع و قواعد حسابداری استخراج شود.

## 16. یکپارچگی مالی و هم‌زمانی

### 16.1 اصل اتمی بودن

عملیات مالی موفق باید به‌صورت اتمیک ثبت شوند. برای یک انتقال موفق، تغییرات لازم در موجودی حساب‌ها، رکورد تراکنش، ورودی‌های تراکنش، ثبت‌های Journal و سایر آثار مالی مربوط باید یا همگی موفق شوند یا همگی rollback شوند.

ثبت ناقص، مانند کاهش ماندهٔ مبدأ بدون افزایش ماندهٔ مقصد یا ایجاد Journal بدون ثبت کامل عملیات، قابل قبول نیست.

### 16.2 ثبت دوطرفه

برای ثبت حسابداری، قواعد کسب‌وکار باید تعادل بدهکار و بستانکار را کنترل کنند. وجود `journal` و `journal_entry` به‌تنهایی اجرای کامل ثبت دوطرفه را اثبات نمی‌کند.

### 16.3 کنترل هم‌زمانی

کنترل هم‌زمانی برای برداشت و انتقال لازم است تا درخواست‌های هم‌زمان نتوانند با خواندن ماندهٔ قدیمی، از محدودیت موجودی عبور کنند.

روش دقیق قفل‌گذاری، ترتیب قفل حساب‌ها و سیاست retry باید از کد واقعی استخراج و در سرویس مالی تعریف شود. این سند روش مشخصی مانند `SELECT FOR UPDATE` را به‌عنوان تصمیم نهایی ثبت نمی‌کند، چون شواهد موجود برای تأیید روش جاری کافی نیست.

### 16.4 تکرار درخواست و idempotency

در سابقهٔ در دسترس، تصمیم نهایی و مستندی دربارهٔ قرارداد idempotency برای درخواست‌های HTTP ثبت نشده است.

این موضوع به‌خصوص برای انتقال وجه باید تعیین تکلیف شود تا retry کلاینت به ثبت دوبارهٔ عملیات مالی منجر نشود.

### 16.5 تطبیق مانده‌ها

ماندهٔ عملیاتی حساب، ماندهٔ سرفصل و Journal باید قابل تطبیق باشند. سازوکار reconciliation، گزارش اختلاف و بازیابی پس از خطا باید به‌عنوان قابلیت مستقل توسعه و آزمایش شود.

- کد شمارهٔ حساب ۱۳ رقم است.
- حساب به نوع حساب، محصول، ارز، شعبه و سرفصل مرتبط می‌شود.

**وابستگی:** به ارز و شعبه نیاز دارد؛ حساب نیز به مشتری وابسته خواهد شد از طریق جداول روابط حساب که در فایل بعدی ایجاد می‌شوند.

### 17.6 `006_account_relationships.sql`

**مسئولیت:** تعریف مالکیت حساب، اختیارها، روابط حقوقی و قواعد امضا.

جداول:

- `account_owner`
- `account_authorization`
- `legal_entity_board_member`
- `legal_entity_shareholder`
- `account_mandate`
- `account_mandate_party`
- `account_mandate_rule`

این جداول روابط زمانی و وضعیت‌های فعال/غیرفعال را نگهداری می‌کنند و برای مالکیت مشترک، نمایندگی، اعضای هیئت‌مدیره، سهام‌داران و ساختار امضا طراحی شده‌اند.

**وابستگی:** به جداول `account` و `customer` نیاز دارد.

### 17.7 `007_balances.sql`

**مسئولیت:** تعریف مانده‌های عملیاتی حساب و ماندهٔ سرفصل.

جداول:

- `account_balance`
- `ledger_account_balance`

مانده‌های حساب شامل ماندهٔ دفتر و ماندهٔ قابل برداشت هستند. ماندهٔ سرفصل شامل مجموع بدهکار، مجموع بستانکار و مانده است.

**وابستگی:** به `account` و `ledger_account` نیاز دارد.

### 17.8 `008_transaction.sql`

**مسئولیت:** تعریف تراکنش و ورودی تراکنش.

جداول:

نوع عملیات، وضعیت، کانال، مبلغ، ارز، مرجع معکوس‌سازی و جزئیات ورودی‌های منبع و مقصد در این فایل تعریف می‌شوند.

**وابستگی:** به ارز و حساب نیاز دارد.

### 17.9 `009_journal.sql`

**مسئولیت:** تعریف Journal، Journal Entry و کارمزد تراکنش.

جداول:

این فایل ثبت حسابداری، بدهکار/بستانکار، ارتباط با تراکنش، سرفصل و کارمزد را تعریف می‌کند.

**وابستگی:** به تراکنش، حساب، ارز و سرفصل دفتر کل نیاز دارد.

### 17.10 `010_financial_consistency.sql`

**مسئولیت:** تقویت سازگاری مالی با کلیدهای یکتا و خارجی مرکب.

این migration کنترل می‌کند که:

- سرفصل والد با ارز سرفصل فرزند سازگار باشد؛
- سرفصل حساب با ارز حساب سازگار باشد؛
- ورودی تراکنش با ارز تراکنش و حساب یکسان باشد؛
- ورودی Journal با ارز سرفصل سازگار باشد؛
- اگر ورودی Journal به حساب متصل است، سرفصل آن دقیقاً همان سرفصل حساب باشد؛
- کارمزد با ارز تراکنش و سرفصل خود سازگار باشد.

همچنین محدودیت قبلی `journal.value_date >= posting_date` را حذف می‌کند تا قواعد تاریخ ارزش در لایهٔ سرویس کسب‌وکار اعمال شوند.

**وابستگی:** به جداول فایل‌های 005، 008 و 009 نیاز دارد.

### 17.11 `011_city_code_global_unique.sql`

**مسئولیت:** یکتایی سراسری کد شهر.

پیش از تغییر، migration وجود کدهای تکراری را بررسی می‌کند. اگر کد تکراری باشد، اجرا متوقف می‌شود. سپس قید یکتایی وابسته به استان حذف و قید یکتایی سراسری `city.code` ایجاد می‌شود.

**وابستگی:** به جدول `city` در فایل 001 نیاز دارد و پس از وجود دادهٔ شهرها قابل اجرا است.

### 17.12 `012_product_ledger_mapping.sql`

**مسئولیت:** تعریف نگاشت زمان‌مند محصول به سرفصل و ثبت نگاشت دقیق مورد استفاده در افتتاح حساب.

جدول:

- `product_ledger_mapping`

این migration:

- از `btree_gist` استفاده می‌کند؛
- نگاشت محصول، نوع حساب، ارز و سرفصل را تعریف می‌کند؛
- بازه‌های زمانی هم‌پوشان یک محصول را منع می‌کند؛
- در صورت وجود چند سرفصل تاریخی برای حساب‌های یک محصول، migration را متوقف می‌کند تا تاریخچه حدس زده نشود؛
- نگاشت‌های لازم برای حساب‌های موجود را backfill می‌کند؛
- `account.product_ledger_mapping_id` را اجباری می‌کند؛
- با کلید خارجی مرکب تضمین می‌کند حساب به همان نگاشت، محصول، نوع حساب، ارز و سرفصل اشاره کند.

**وابستگی:** به محصول، نوع حساب، ارز، سرفصل و حساب در فایل 005 نیاز دارد و پس از تعریف محدودیت‌های سازگاری مالی فایل 010 نیز باید در چارچوب ترتیب migration پروژه اجرا شود.

### 17.13 ترتیب کلی

ترتیب شناخته‌شدهٔ فایل‌ها از `001` تا `012` است. فایل‌های 002 و migrationهای بعدی باید فقط در ترتیب تعریف‌شده و با توجه به وضعیت واقعی پایگاه داده اجرا شوند.

وجود شمارهٔ فایل به معنی ثبت موفق آن در هر پایگاه دادهٔ محلی یا محیط دیگر نیست. وضعیت migrationهای اعمال‌شده در محیط جاری باید جداگانه بررسی شود.

## 18. ساختار کد و قرارداد API

### 18.1 مسیرهای اصلی

- `src/domain/`
- `src/application/`
- `src/infrastructure/repository/`
- `src/infrastructure/`
- `src/web/`
- `database/schema/`

نام و رفتار دقیق کلاس‌ها باید از نسخهٔ مورد بررسی GitHub یا commit مشخص استخراج شود. این سند نام کلاس‌هایی را که در نسخهٔ خاصی مشاهده نشده‌اند، به‌عنوان قابلیت قطعی معرفی نمی‌کند.

### 18.2 قرارداد پاسخ HTTP

کد از کلاس‌های `HttpResponse` و `ApiResponse` استفاده می‌کند. قالب دقیق JSON، نام فیلدها و شکل خطا باید از فایل‌های واقعی این کلاس‌ها استخراج شود.

برای هر endpoint باید موارد زیر مستند شوند:

- متد HTTP و مسیر؛
- ورودی JSON و query parameterها؛
- اعتبارسنجی‌ها؛
- پاسخ موفق و کد وضعیت؛
- خطاهای کسب‌وکار؛
- خطاهای پایگاه داده؛
- الزامات مجوز و احراز هویت، پس از پیاده‌سازی آن‌ها.

### 18.3 endpointهای شناخته‌شده

در نسخهٔ قابل مشاهدهٔ مخزن، مسیر سلامت `GET /api/v1/health` در README مستند شده است. در سابقهٔ توسعه نیز endpointهای مشتری، ارز، کشور، استان، شهر و شعبه مطرح شده‌اند.

وجود endpoint در router با تکمیل کامل رفتار، امنیت یا تست آن یکسان نیست. فهرست دقیق APIهای فعال باید با کد همان commit و نتیجهٔ درخواست HTTP به‌روز شود.

### 18.4 API نوع حساب

در تغییر محلی اخیر، مسیرهای زیر هدف قرار گرفته‌اند:

- `POST /api/v1/account-types`
- `GET /api/v1/account-types`
- `GET /api/v1/account-types/{id}`
- `PATCH /api/v1/account-types/{id}/status`

کاربر build و اجرای برنامه را پس از تغییرات گزارش کرده است؛ اما نتیجهٔ HTTP برای این مسیرها هنوز در سابقهٔ حاضر ثبت نشده است. بنابراین این API در وضعیت «کد محلی گزارش‌شده و build موفق به گزارش کاربر؛ آزمایش HTTP در انتظار» قرار می‌گیرد.

- وجود جدول در اسکیما به معنی تکمیل سرویس متناظر نیست.
- commit محلی با commit ثبت‌شده در GitHub یکسان فرض نشود مگر آنکه SHA تطبیق داده شده باشد.
- هیچ نتیجهٔ تستی بدون شواهد به‌عنوان موفق ثبت نشود.

## 24. روش نگهداری سند

`docs/PROJECT_CONTEXT.md` باید مرجع عملیاتی شروع هر گفت‌وگوی جدید باشد.

پس از هر تصمیم مهم یا مرحلهٔ توسعه:

1. وضعیت تصمیم یا قابلیت به‌روزرسانی شود.
2. فایل، commit یا نتیجهٔ تستی که تغییر را پشتیبانی می‌کند ثبت شود.
3. وضعیت محلی و GitHub جداگانه بررسی شوند.
4. موارد باز حذف نشوند مگر اینکه واقعاً حل شده باشند.
5. تاریخ بازبینی سند و commit مبنای آن به‌روزرسانی شود.

در آینده می‌توان `docs/DECISIONS.md` را برای تاریخچهٔ تصمیم‌ها و دلیل انتخاب‌ها ایجاد کرد. فعلاً تمام اطلاعات اصلی در همین سند نگهداری می‌شود.
