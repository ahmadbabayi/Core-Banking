## 1. هدف و وضعیت پروژه

Core Banking یک backend بانکی مبتنی بر C++ و Qt با پایگاه دادهٔ PostgreSQL و رابط HTTP/JSON است.

دامنهٔ هدف شامل مدیریت مشتری، ارز و شعب، نوع حساب و محصول، سرفصل دفتر کل، نگاشت محصول به سرفصل، افتتاح حساب، مالکیت و اختیارات، تراکنش، ثبت حسابداری، مانده‌ها و کنترل یکپارچگی مالی است.

پروژه در حال توسعه است و نباید آمادهٔ بهره‌برداری واقعی بانکی فرض شود.

## 3. تصمیم‌های معماری و کسب‌وکار

### 3.1 مشتری و Customer Management

- Core Banking از سامانهٔ Customer Management جداست.
- Core Banking اطلاعات ضروری مشتری را برای عملیات بانکی نگهداری می‌کند؛ عملیات عادی نباید به استعلام لحظه‌ای از Customer Management وابسته باشد.
- شناسهٔ داخلی از نوع `BIGINT` است، نه UUID.
- شمارهٔ مشتری ده‌رقمی و یکتا است.
- نوع مشتری `INDIVIDUAL` یا `LEGAL_ENTITY` است.
- شخص حقیقی و حقوقی در جداول جداگانه نگهداری می‌شوند.
- `nationality_code` سه‌رقمی و مرتبط با `country(code)` است.
- وضعیت مشتری: `ACTIVE`، `INACTIVE`، `BLOCKED` یا `CLOSED`.
- مالکیت مشترک، رابطه‌ای در سطح حساب است، نه نوعی از مشتری.

قرارداد همگام‌سازی، مالکیت فیلدها و رفتار خطا بین دو سامانه باید در صورت نیاز جداگانه نهایی شود.

### 3.2 جغرافیا، شعب و ارز

- کد کشور سه‌رقمی است.
- کد شهر در کل جدول شهرها یکتا است.
- کد شعبه هفت‌رقمی است: سه رقم بانک و چهار رقم شعبه.
- ارز کد سه‌حرفی و کد عددی سه‌رقمی دارد.
- نوع حساب و محصول باید ارز سازگار داشته باشند.
- ارز محصول از رابطهٔ آن با نوع حساب قابل تعیین است؛ بدون نیاز کسب‌وکاری، مدل مستقل `product_currency` ایجاد نشود.

### 3.3 نوع حساب و محصول

کدهای نوع حساب مطرح‌شده در طراحی:

- `01`: جاری
- `02`: کوتاه‌مدت
- `03`: پس‌انداز
- `04`: بلندمدت
- `21`: دولتی
- `31`: شهرداری
- `41`: مدارس و سازمان‌های دولتی

کدها و داده‌های مرجع باید با Schema و داده‌های واقعی تطبیق داده شوند.

محصول دارای کد یکتا، نام، نوع حساب، ارز، وضعیت و بازهٔ اعتبار است. تاریخ پایان می‌تواند خالی باشد و در صورت وجود نباید قبل از تاریخ شروع قرار گیرد.

### 3.4 حساب

- شمارهٔ حساب سیزده‌رقمی و یکتا است و سرور آن را تولید می‌کند.
- الگوی شماره‌گذاری و رقم کنترل باید از پیاده‌سازی واقعی استخراج و تست شود؛ فرمول نباید حدس زده شود.
- هر حساب دقیقاً یک سرفصل دفتر کل دارد.
- انتخاب سرفصل نباید بر اساس شناسهٔ هاردکدشده باشد.
- افتتاح حساب باید محصول، نوع حساب، ارز، شعبه، مشتری و نگاشت معتبر سرفصل را کنترل کند.
- ایجاد حساب، رابطهٔ مالکیت و ماندهٔ اولیه باید اتمیک باشد.
- ماندهٔ اولیهٔ حساب جدید صفر است؛ برای افتتاح صفرمانده نباید ثبت حسابداری مالی جعلی ایجاد شود.

### 3.5 مالکیت و اختیارات

مدل روابط حساب برای مالکیت مشترک، وکالت، سرپرستی قانونی، نمایندهٔ حقوقی، امضاداران مجاز، اعضای هیئت‌مدیره، سهام‌داران و قواعد امضا طراحی شده است.

صرف وجود این جداول، تکمیل موتور ارزیابی اختیارات را ثابت نمی‌کند. اعتبار زمانی اختیار، نوع عملیات و تعداد امضاهای لازم باید در سرویس‌های مربوطه کنترل شوند.

### 3.6 دفتر کل و نگاشت محصول

- کد سرفصل دفتر کل هشت‌رقمی است.
- دسته‌های سرفصل: `ASSET`، `LIABILITY`، `EQUITY`، `REVENUE` و `EXPENSE`.
- ارز حساب، سرفصل و ثبت مالی باید سازگار باشد.
- نگاشت محصول به سرفصل زمان‌مند است.
- نگاشت معتبر در تاریخ افتتاح باید پیدا و شناسهٔ همان نگاشت در حساب ثبت شود.
- نگاشت‌های دارای بازهٔ زمانی هم‌پوشان مجاز نیستند.
- تاریخچهٔ نگاشت‌ها نباید با تغییر تنظیمات جدید به‌طور ناخواسته بازنویسی شود.

### 3.7 مانده و ثبت مالی

- `account_balance` ماندهٔ دفتر و ماندهٔ قابل برداشت را نگهداری می‌کند.
- `ledger_account_balance` خلاصهٔ بدهکار، بستانکار و ماندهٔ سرفصل را نگهداری می‌کند.
- نوع مالی تعریف‌شده در Schema، `NUMERIC` است؛ precision/scale نهایی، گردکردن و سیاست پولی باید با تصمیم قطعی و کد جاری تطبیق داده شوند.
- تراکنش مالی باید اتمیک باشد.
- ثبت حسابداری باید بدهکار و بستانکار متوازن داشته باشد.
- برداشت و انتقال باید در برابر درخواست‌های هم‌زمان ایمن باشند.
- قرارداد idempotency و سازوکار reconciliation باید تکمیل و آزمایش شوند؛ وضعیت تکمیل آن‌ها نباید فرض شود.

## 4. مرجع Schema

تمام فایل‌های زیر در `database/schema/` مرجع ساختار پایگاه داده‌اند. جزئیات و محدودیت‌های هر جدول باید مستقیماً از همان فایل خوانده شود.

| فایل | موضوع |
|---|---|
| `001_geography_currency.sql` | کشور، استان، شهر، شعبه و ارز |
| `002_remove_legacy_tables.sql` | حذف جداول قدیمی؛ migration مخرب و نیازمند احتیاط |
| `003_customer.sql` | مشتری، شخص حقیقی و شخص حقوقی |
| `004_customer_number_and_indexes.sql` | شمارهٔ ده‌رقمی مشتری و ایندکس‌ها |
| `005_account_product_ledger.sql` | نوع حساب، محصول، سرفصل و حساب |
| `006_account_relationships.sql` | مالکیت، اختیارات، روابط حقوقی و امضا |
| `007_balances.sql` | ماندهٔ حساب و ماندهٔ سرفصل |
| `008_transaction.sql` | تراکنش و ورودی تراکنش |
| `009_journal.sql` | Journal، Journal Entry و کارمزد |
| `010_financial_consistency.sql` | محدودیت‌های یکپارچگی مالی |
| `011_city_code_global_unique.sql` | یکتایی سراسری کد شهر |
| `012_product_ledger_mapping.sql` | نگاشت زمان‌مند محصول به سرفصل و اتصال حساب به نگاشت |

ترتیب migration و وضعیت اعمال‌شدن آن‌ها در هر محیط باید بررسی شود. فایل‌های حذف یا تغییر ساختاری نباید بدون بررسی داده‌ها و ترتیب اجرا روی محیط مهم اجرا شوند.

این موارد، گزارش تاریخی هستند؛ وضعیت جاری باید در صورت نیاز دوباره بررسی شود.

### 5.2 Product Management API

Commit مرتبط در سابقه:

`7ca1fd9` — `Implement product management API`

مسیرها:

- `POST /api/v1/products`
- `GET /api/v1/products`
- `GET /api/v1/products/{id}`
- `PATCH /api/v1/products/{id}/status`

فیلترهای فهرست: `status`، `accountTypeId` و `currencyId`.

فیلدهای ایجاد: `code`، `name`، `accountTypeId`، `currencyId`، `effectiveFrom` و `effectiveTo` که می‌تواند `null` باشد. وضعیت پیش‌فرض `ACTIVE` است.

تست‌های HTTP گزارش‌شده شامل ایجاد، فهرست، دریافت، فیلتر، کد تکراری، تغییر وضعیت و اعتبارسنجی ورودی‌ها هستند. پاسخ‌های موفق و خطاهای `200`، `201`، `400` و `409` در این تست‌ها گزارش شده‌اند.

محصول آزمایشی ثبت‌شده:

- کد: `TEST-CURRENT-IRR`
- شناسه: `1`
- وضعیت: `ACTIVE`
- `accountTypeId`: `1`
- `currencyId`: `1`
- `effectiveFrom`: `2026-10-12`
- `effectiveTo`: `null`

این محصول برای تست‌های بعدی حفظ شود؛ قبل از فرض وجود آن در محیط دیگر، پایگاه داده بررسی شود.

### 5.3 موارد نیازمند بررسی

- نتیجهٔ HTTP فعلی API نوع حساب باید ثبت شود؛ موفقیت Build به‌تنهایی تست API نیست.
- وضعیت کامل API سرفصل دفتر کل باید از کد بررسی شود.
- Product–Ledger Mapping API هنوز مرحلهٔ بعدی توسعه است و نباید تکمیل‌شده فرض شود.
- افتتاح حساب باید با نگاشت سرفصل، روابط مالکیت و ماندهٔ صفر یکپارچه و آزمایش شود.
- انتقال مالی به تست هم‌زمانی، idempotency و سازگاری Journal نیاز دارد.
